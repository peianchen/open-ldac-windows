# 開發紀錄與心得

這是依原始碼提交、建置與實際測試整理的工程紀錄。
開發者提出需求與安裝界線，AI 工具協助規劃、實作、查閱文件、操作測試與整理記錄。
完成判定依實際工具輸出與證據，不把產生程式碼視為驗證完成。

記錄日期截至 2026-11-04，使用 Asia/Taipei 日曆日期。
GitHub Actions 可能以 UTC 顯示前一天；VM 除錯時鐘也不適合做效能比較。
這份紀錄的心得是從專案事件得到的工程反思，沒有虛構使用者聽感或量測結果。

## 起點：想在現有筆電上做開源 LDAC

需求是保留內建藍牙，初步以 MediaTek 與 WH-1000XM6 為目標，開源至 GitHub。
對筆電而言，音質與耗電都要考慮，後續明確以音質優先，並加入使用者可調碼率。

先確定幾件事情：編碼器、Bluetooth profile transport、完整 AVDTP、Windows 音訊端點
與安裝簽章是不同的工作。只有編碼器不會在 Windows 聲音設定中自動出現 LDAC。
因此先做可以離線重現的最小核心，再逐步擴大驗證範圍。

## 為什麼花時間在關閉與取消

最初要解決的問題不是多送一個封包，而是關閉失敗時誰還可能使用物件。
只要仍有 OPEN、資料要求或提供者回呼，檔案已關閉也不能立即釋放根物件。
若以超時來猜測「應該不會再回呼」，就會把偶發的晚到事件變成核心記憶體錯誤。

實作上改成分開記錄 owner、OPEN、provider、data、CLOSE 與 active-call 持有權。
取消在鎖外執行，送出前後檢查取消意圖，回呼真正退場才放掉對應持有權。
不確定的資源保留有上限，狀態也必須可觀察。

**心得：錯誤處理需要和正常路徑一樣具體。**
「失敗就 cleanup」不是完整設計，要能說清楚何時禁止新工作、何時要求取消、
誰負責最後完成，以及哪個事件能證明記憶體不會再被碰到。

## 主機模型很有用，但替代不了核心測試

共享的生命週期模型能快速排列事件順序；把實際傳輸函式編進主機 shim，
又能測到接合層錯誤。移除路徑重複送 CLOSE 就是在這一層先抓到。
ASan／UBSan 也能在適用的使用者模式測試中檢查記憶體與未定義行為。

但真實 WDF 的物件內容、執行層級與要求初始化不由 shim 決定。
第一次 VM 核心測試仍發生當機，正好指出模型邊界：
測試驅動把主要求配置成 port 的 8-byte context，主傳輸取不到預期的 512-byte context。

**心得：不同層級的測試各自回答問題，不能把綠燈相加就叫實機相容。**
每個結果都要帶上環境、版本、觸發條件與沒有涵蓋的部分。

## 從核心當機回到一個可修的原因

單靠 0x3B 無法知道是提供者、要求生命週期還是初始化出錯。
第一次預定的 dump 又沒有成功落盤，所以先修好診斷路徑，
用虛擬 COM、精確 PDB、WDF handle 與 IFR 觀察同一個失敗。

實際證據把問題縮成一個語意差異：WDF context 初始化巨集包含兩個敘述，
else 沒有大括號，後半段便無條件覆寫主裝置的 context 類型。
補上大括號後，再執行同一 runner，才得到可比較的修正前後結果。

**心得：符號、當機檔與資料完整性是開發環境的一部分。**
不是等出錯後才想辦法找一個差不多版本的 PDB；也不能忽略讀回來已經損壞的 JSON。
這次因此補上 artifact 雜湊、SYS／PDB identity、私有 dump 保存及無效證據標記。

## VM 設定也會製造雜訊

滑鼠問題來自 USB Tablet 與控制器設定不一致；客體帳號名稱也沒有保證真正具備管理員群組。
安裝媒體沒退出又可能讓冷啟動回到安裝程式。這些問題需要逐項確認實際狀態，
而不是把所有黑畫面或卡住都歸咎於驅動。

暖重新啟動黑畫面的根因仍沒有完整證明。這次採已驗證可用的正常關機／冷啟動路徑，
並保留原 VM，不把一個 workaround 寫成完整修復。

**心得：先確認觀察與控制能力，再開始會故意製造故障的測試。**
權限、GuestControl、復原快照、dump 與除錯器準備好，才有可靠的回饋循環。

## 音質優先也要有可以檢驗的定義

HQ 預設、保留相容來源取樣率、電池不自動降碼率，是目前能明確實作與測試的政策。
事件驅動、空閒停止編碼、有上限緩衝，是後續即時路徑要滿足的工程要求。
至於聽起來是否更好、RF 重傳是否增加、筆電多耗多少電，都還需要分開量測。

**心得：規格數字、演算法輸出與使用者體驗之間需要實驗連結。**
不以 96 kHz、990 kbps 或某次 CPU 時間直接推導成普遍的音質與續航優勢。

## 2026-11-03：完成要求不等於檔案已退休

原先的合成提供者立即完成 OPEN，無法回答連線進行中取消會發生什麼事。
新版本使用 manual queue 與提供者持有的 pending request，控制取消、成功／失敗、
file cleanup 與 callback retirement 的先後，並加入取消與 retrieve 同時競爭的案例。
三輪各6,343 checks、140個新案例通過；實際來源、SYS/PDB、作用中規則與正常卸載
記錄在[本輪實驗報告](validation/KERNEL_LAB_2026-11-03.md)。

過程先被 CI 的 C6011 擋下，修正所有權路徑後，實際基準又在第12個案例開檔時
遇到檔案數上限。沒有把它當作無關的環境問題跳過，也沒有提高上限。
測試原先把 root歸零／完成通知當作可以立即重開的條件，這比真正的檔案退休更早。
後續先關閉 IOCP 等案例 handle，再觀測 WDF 的 active_files；基準確實記錄到有限的
延後退休等待。這修正了測試的觀測條件，不代表正式驅動已保證關閉後立即重開。

另一個容易誤判的地方是 oneboot：這次開機後 `/querysettings` 顯示下次啟動的空設定，
但 `/query` 仍可證明本次執行中的規則與模組。驗證腳本先因這個差異擋住下一步，
再改為串起開機前設定、實際開機時間、套件雜湊與 runtime，而不是降低驗收條件。

**心得：測試工具自己的要求、執行緒與檔案也有生命週期。**
因此失敗時直接結束整個 runner process，避免仍存活的 worker 寫入已離開的堆疊；
不同 status布局增加 ABI版本，基準與卸載紀錄綁定二進位身分，成功／失敗結果都先
匯出才還原快照。這些能提高可重現性，仍不能代替耳機音質或筆電耗電的實測。

## 2026-11-04：讓低資源測試回答「實際失敗在哪裡」

前一輪補了延後 OPEN 與強制 pending，仍不能回答真實框架配置不足時如何清理。
這次使用 KMDF 的 `VerifierAllocateFailCount`，以 `969a9ef` 的新 SYS／PDB／runner
依序測試 0 到 128 的配置門檻。每個門檻重新 load，以不同 nonce 綁定 464-byte、
version 2、24-site FINAL；進度記錄或上一輪的殘留資料不能替代最終證據。

觀測層只記錄真實 WDF 回傳值，不把成功呼叫改成失敗。本輪 80 次啟動失敗，
49 次啟動後進入 workload；所有門檻都完成指定資源歸零、callback 平衡與退場條件。
十個必要執行期站點全部有實際資源失敗，共 44 次，初始化站點另有 80 次。
合計 124 次失敗呼叫，分布於 18 個站點與 102 個門檻，實際 NTSTATUS 皆為
`0xC000009A`。它們不是 124 次相互獨立的隨機或 DIF 注入。

有兩個很容易寫錯的例子：n=80 的 CreateFile 回報資源錯誤，但本輪站點沒有命中，
所以不能憑預測替 file-lock 增加覆蓋；n=101／102 的 runner API 沒有資源錯誤，
close-format 卻各失敗兩次，必須從核心站點與最終 provider retirement 才看得見。
因此 API 層的 25 次預期資源錯誤，與站點的 124 次失敗保留為不同統計口徑。

基準與移除低資源條件後的恢復輪各通過 6,343 checks、140 個延後 OPEN 案例，
callback add／release 各 173，roots destroyed 173。Verifier runtime 只列測試模組，
標準旗標 `0x001209bb`，最後 load 130／unload 130；其集區計數為零，沒有被解讀
成所有 WDF 配置均已追蹤或不存在洩漏。random／systematic DIF 仍未測。
這組新版證據也沒有借用 `4437db1` 的前輪成功數字。

過程的另一個失敗來自收集器：`Win32_SystemDriver` WMI 查詢卡住，使前置流程
無法完成。改用 native SCM 與 registry 查詢後，在相同套件與驗收輸入下重新執行
才通過；沒有修復／重設 WMI 或修改日用主機，也沒有把卡住那次當成功。

**心得：故障注入設定、API 錯誤與站點正向命中，是三種不同的證據。**
研究式紀錄需要寫出分母、門檻、觀測範圍與未命中處；預測沒有發生時，就留下
缺口，而不是替數字找一個看似合理的解釋。完整方法、24 站點表與公開原始 FINAL
資料見[低資源實驗報告](validation/KERNEL_LOW_RESOURCE_2026-11-04.md)。

匯出來源、結果、八份 stage JSON、公開測試憑證與已簽署 SYS 後，還原乾淨快照，
再以新啟動核對服務／標記／憑證皆無專案測試狀態、Secure Boot 開啟、BCD 測試
簽章／除錯關閉、Verifier 沒有目標驅動，最後正常關機；保留 VM 與快照供後續使用。
低資源 gate 已允許接續播放協定開發；真實 BthPort／XM6、Windows 音訊
端點、聽感與耗電仍待驗證。HQ 音質優先、手動碼率與電池不自動降級持續保留。

## 2026-11-04：通過低資源門檻後，開始播放協商

低資源驗證通過後，才開始有界 AVDTP initiator 的離線開發。它依序查詢候選端點，
要求 LDAC 立體聲與來源採樣率精確一致，再經過設定、OPEN、媒體通道 ready、START。
沒有重採樣器時，不把 fallback 的編碼率當成已轉換的 PCM；HQ／手動碼率政策另外保留。

單筆交易用 label、signal 與通道 generation 比對，本地逾時／send callback 另帶 serial。
審查指出無關回應若先被完整解析，可能錯誤終止目前交易；修正為可讀單封包先核對 tuple。
新增回歸測試後，也修正舊 fixture 對 reserved-signal 無關回應的矛盾期待，沒有放寬
匹配封包的長度／拒絕檢查。最終協定測試通過 4,837 項 CHECK，另有 5,805 core、
18,976 lifecycle／1,020 模型排程、7,532 adapter host-shim 與104個檔案整合案例通過。

**心得：協商完成、通道可用、PCM 格式正確與實際播放，是不同的接受條件。**
這個模組沒有 heap、背景執行緒或定時輪詢，但也尚未整合真實通道與音訊端點；不能
從離線檢查數推算聲音或電力成果。四位元交易標籤重用後無法辨識任意古老同 tuple，
因此逾時要汰換整個通道世代，而不是宣稱本地 serial 已改變遠端 wire 格式。
契約、已執行測試與互通限制見[協商模組說明](AVDTP_SESSION.md)。
