# 播放尾段與正常 CLOSE 驗證（2026-11-06）

本輪完成發送端尾段等待及正常 AVDTP CLOSE 的整合。已通過本機與隔離 Windows VM
的軟體／服務測試，尚未建立 XM6 實際播放、接收端尾音完整性或實機 L2CAP 關閉證據。
來源基底為 `7c39d232cfd73bf82ee0df90bf24eeb98adbff42`；本報告所在 commit 是修改版本。
精確執行檔及 60 個建置輸入的 SHA256 見[機器可讀紀錄](graceful-close-2026-11-06.json)。
輸入雜湊對應測試時工作樹位元組，可能與 Git 正規化換行後的 blob 不同。

## 問題與修正原理

舊版只等編碼樣本的名義結束時間；最後一包若較晚完成傳送，可能立刻進入關閉。
新版 `finish_media` 等待以下兩個期限的較晚者：

- 首包時間基準加全部成功傳送的編碼樣本時長。
- 最後一次完整成功 WriteFile 完成的 QPC 時間，加最後一包編碼樣本時長。

時間轉換向上取整，檢查整數溢位；每次喚醒重查 QPC。等待使用一次性計時器與
停止／訊號事件，不設定全域計時解析度、不忙碌輪詢。串流原有 40 ms 遲到失敗
保護維持；終端等待允許較晚完成，避免把「已過名義期限」誤當成不用等尾段。
這只建立發送端時間下限，沒有猜測耳機的接收緩衝延遲。

正常 EOF 改為 CLOSE，取代 SUSPEND＋ABORT。新增狀態不改舊數值：
`CLOSE → WAIT_MEDIA_CLOSE → CLOSED`。收到相符且合法的接受回覆才關閉本機
媒體 handle，再回報本機所有權已釋放，最後釋放 signaling。失敗或取消仍安全
收尾，不為了顯示成功而強送另一筆 CLOSE／ABORT。

CLOSE 接受、本機 handle 釋放、底層 BRB／遠端 L2CAP 完成斷線是不同事件。
本輪只驗證前兩者的使用者模式流程；沒有修改 kernel、INF 或原生 ABI，
不能宣稱已滿足真實傳輸的完整關閉程序。

CHECK 是輔助斷言與重複流程總數，並非獨立測試情境數。正常 EOF 少了一組
SUSPEND/ABORT 交易，因此原有自動故障注入迴圈數量隨流程改變；新增明確收尾斷言。

重點回歸包含：空來源／短尾段、CLOSE accept 前不得釋放媒體、尾段等待失敗不得
送 CLOSE、拒絕／畸形 CLOSE 回覆、遲到最終傳送與未到的名義終點各自較晚時的
等待下限。管線背壓測試記錄成功寫入完成晚於延遲讀取者的 QPC，沒有量測並宣稱
每次 I/O 的 pending 時長。正向等待不設定脆弱的 VM 即時排程上限。

測試工具鏈為保留的 Zig 0.14.1 Windows x64。協定與 I/O 模組另以 `-Werror`
檢查；完整建置及 VM 使用最終 SHA256 固定套件。獨立唯讀審查未發現阻擋問題，
提出的正常關閉順序、等待失敗及兩種期限分支測試均補齊。

## 執行過程與限制

初次 GuestControl 在開機期間尚未就緒，當時畫面為黑畫面；後續服務自行就緒，
本輪沒有因此強制關機。乾淨快照沒有上輪 package 目錄，建立專用目錄後完成傳入。
第一次傳入檢查器使用相對路徑失敗，改為絕對路徑；文件讀取遇到 Windows cp950，
改用明確 UTF-8。這些是工具／環境準備問題，沒有把失敗輸出計為測試通過。

HQ 仍為預設，保留手動 990/660/330 或 909/606/303 kbps（依來源採樣率家族）；
電池不自動降級、不強制升頻。尚未量測真實耳機音質、耗電、延遲、RF 重傳、
PnP／睡眠恢復，也尚無 Windows 系統音訊端點或正式簽章安裝包。
本輪沒有在日用筆電安裝實驗驅動或服務。

下一個實機門檻仍包括 prepared/signed/recoverable 傳輸目標、對端命令與封包
分段處理、BRB 關閉證據、接收端 delay／尾音捕捉，以及 Windows PCM 來源整合。
目前測試成功不授權跳過這些條件安裝到日用筆電。

## 規格依據

Bluetooth SIG [AVDTP TS p22](https://files.bluetooth.com/wp-content/uploads/dlm_uploads/2025/02/AVDTP.TS_.p22.pdf)
§4.3.1.14／4.3.1.43 提供 CLOSE 接受、媒體傳輸釋放的順序及拒絕格式依據。
本輪核心規格下載連結未能讀取；測試套件是官方依據，但本專案未取得 SIG 認證。
Windows I/O 的取消／退休契約沿用[既有說明](../PLAYBACK_SERVICE.md)。
