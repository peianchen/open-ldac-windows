# 第二次主機重啟後 USB ETW 實驗：2026-11-06

## 結論

主機已在前輪 PnPUtil 3010 之後重啟。本輪仍未通過 guest USB 入口：`usbattach` 回傳 0，但 VM 實際附掛為 false，guest 正常盤點的目標 USB 數為 0，Bluetooth class 數也為 0。**尚未找到確定根因，也沒有進行 XM6 配對、LDAC 播放或主機實驗性驅動安裝。**

[機器可讀結果](usb-etw-2026-11-06.json)保留本輪時間與觀察；[前輪實驗](POST_REBOOT_USB_2026-11-06.md)保留原始歷史，不將後來的重啟回填成先前成功。

## 方法

確認主機開機時間為 14:37:30.500 UTC、VBoxUSBMon Running，MediaTek／XM6 原 INF、服務、版本與狀態一致。Guest 命令通道就緒後，對唯一 VID 0489／PID E0F6 裝置執行一次有界移交；VM 使用 xHCI，等待約 30 秒並獨立讀取 guest 裝置盤點。沒有新增持久 USB filter 或廣泛重設 hub。

ETW 使用 USBHUB3、UCX、USBXHCI 與 Kernel-PnP，限制 180 秒／64 MB 環形檔，實際約 53 秒。未啟用 USB 封包標頭、部分資料或完整資料關鍵字。trace 啟停均回傳 0、未達自動停止期限；tracerpt 處理 4,867 事件、遺失 0。Get-WinEvent 解析 4,866 筆；兩個解碼器的計數不同，分別保留，不混用。零遺失不代表所有可能相關 provider 都有啟用。

## 事件關聯與反證

使用 USB rundown 的完整目標介面識別來取得該次 trace 的裝置指標，再按欄位精確關聯；不把包含 VID 字串片段的任意事件算成目標。原始指標與裝置序號只保留本機。

- 目標是實體 port 3。與目標裝置指標直接匹配的 USB 事件沒有 Error／Warning／Critical 等級事件；這不能排除其他層級或其他 provider 的失敗。
- 目標 Kernel-PnP 只有事件 220／222。從本機 provider 定義核對，這是查詢 bus relations 的開始／結束，並非裝置重啟成功事件。
- 全 trace 的 12 筆錯誤等級事件不能直接歸因於 MediaTek。兩組暫時裝置指標後續的事件 61 分別指向 port 4、5；另一組含其他裝置的 vendor/product 欄位。沒有把它們當作目標 port 3 的失敗原因。
- VBoxSVC 記錄曾建立目標捕捉規則，之後 USB 列舉顯示 captured 0；VM log 沒有成功附掛該實體裝置的證據。host 清單的 Captured 與指令 exit 0 均不足以通過入口判定。
- detach 回傳 1，訊息為裝置未附掛。恢復判定使用獨立 host PnP 與驅動綁定比對，不將 detach 當成功。

目前可定位到 host capture／VM attach 入口仍失敗；無法僅憑這份 ETW 在 Windows 拒絕移交、VirtualBox proxy 流程或控制器特殊行為之間確定原因。Guest 根本看不到目標，不能將問題歸因於 LDAC 編碼品質或播放服務。

## 恢復與資料保留

VM 正常關機後還原既有 clean snapshot，恢復原 OHCI USB tablet 設定，EHCI／xHCI 關閉，VM 保持 poweroff。MediaTek、XM6、複合 USB 裝置狀態均 OK，原綁定一致。本輪還原後未再開機重跑 guest clean runtime 檢查，不新增這項通過宣稱。

私有 ETL、解碼事件與 VBox log 保留專用驗證資料夾，不上傳 GitHub；公開檔案只包含去識別統計、結果與 ETL SHA-256。原始碼、既有驗證結果及 VM 保留。音質優先、手動碼率與既有 pacing 防護未修改。本輪是環境驗證，未重跑軟體回歸，亦無音質／耗電實測。
