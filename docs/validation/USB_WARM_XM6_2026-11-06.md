# 內建藍牙喚醒、USB 移交與 XM6 服務發現：2026-11-06

本階段首次取得同一顆內建藍牙控制器實際進入 Windows 虛擬機、guest 藍牙正常列舉、XM6 配對成功，以及 Audio Sink SDP 查詢完成的證據。**這是實體控制器與服務發現驗證，尚不是原生 LDAC 驅動載入、AVDTP 協商或耳機播放驗證。**

本報告的觀察截止點為 2026-11-06 15:51 UTC。後續 snapshot、簽章及原生驅動安裝是另一階段，不由本文預先宣告成功。[可公開摘要](usb-warm-xm6-2026-11-06.json) 列出各項證據與未完成門檻；裝置位址、序號、VM 識別碼、帳密、配對金鑰及原始記錄保留於本機私有目錄。

## 1. 研究問題與判定方式

前次實驗中，`VBoxManage usbattach` 回傳 0，主機清單顯示 `Captured`，但 VM 實際附掛清單為空，guest 也看不到控制器。補齊 Oracle USB Support、重新啟動與精確 filter 比對都不足以單獨解決。相關失敗保留於[先前實體通道報告](PHYSICAL_TRANSPORT_2026-11-06.md)及[重啟對照報告](POST_REBOOT_USB_2026-11-06.md)，不以後來成功覆寫。

問題分成四層，各自需要不同證據：

| 層級 | 通過條件 | 不能據此宣稱 |
| --- | --- | --- |
| 主機 USB 捕捉 | VM 實際附掛 UUID 符合目標，且主機出現健康的 VirtualBox USB proxy | guest 藍牙可用 |
| guest 控制器 | 目標 USB 子裝置列舉，藍牙 radio 由 BTHUSB 正常服務 | 耳機已配對或能播放 |
| 耳機與服務 | 配對 API 成功，Audio Sink SDP 列舉完整，建立實際服務 PDO | LDAC 編碼器、雙 L2CAP 通道或音質通過 |
| 原生播放 | 原生套件合法載入、實際 AVDTP 與媒體傳輸、資源退休及實際聆聽 | 未測條件下的穩定性或耗電表現 |

## 2. 從官方原始碼形成假說

檢查使用 Oracle 官方 VirtualBox 7.2.22 release commit `1a6d24cb4a45f57aabfbad86811553e004f060f7`，對應 r175245。選讀檔案、來源網址和 SHA-256 已保留於本機研究資料；沒有執行下載的程式，也沒有更換主機驅動。

`USBProxyBackendWindows::captureDevice` 先加入一次性 filter，再要求 monitor 執行比對。這個回傳點不等待實體裝置完成移交；monitor 掃描中的個別失敗也不一定傳回使用者模式。因此命令成功只能視為請求獲得處理，不能作為完成證據。[captureDevice 原始碼](https://github.com/VirtualBox/virtualbox/blob/1a6d24cb4a45f57aabfbad86811553e004f060f7/src/VBox/Main/src-server/win/USBProxyBackendWindows.cpp#L145)、[filter 掃描原始碼](https://github.com/VirtualBox/virtualbox/blob/1a6d24cb4a45f57aabfbad86811553e004f060f7/src/VBox/HostDrivers/VBoxUSB/win/mon/VBoxUsbFlt.cpp#L1147)

主機狀態轉換程式還會把部分 Capturing／AttachingToVM 過渡狀態對外呈現為 Captured。實際機制則需要 USB 裝置重新列舉成 VirtualBox proxy、由 VBoxUSB 服務接管，再附掛到 VM。[狀態映射](https://github.com/VirtualBox/virtualbox/blob/1a6d24cb4a45f57aabfbad86811553e004f060f7/src/VBox/Main/src-server/HostUSBDeviceImpl.cpp#L2562)、[monitor 設計說明](https://github.com/VirtualBox/virtualbox/blob/1a6d24cb4a45f57aabfbad86811553e004f060f7/src/VBox/HostDrivers/VBoxUSB/win/mon/VBoxUsbMon.cpp#L45)

描述子讀取路徑直接向所取得的 PDO 傳送內部 USB 請求，該函式沒有顯式的喚醒 power IRP。先前 ETW 時序顯示目標在捕捉前已離開 D0，這與「閒置電源狀態可能影響捕捉」相容，但不足以證明唯一根因。官方程式也存在描述子逾時後加入動態排除名單的路徑；本次沒有讀到該名單內容，不能宣稱已證實命中。[描述子讀取](https://github.com/VirtualBox/virtualbox/blob/1a6d24cb4a45f57aabfbad86811553e004f060f7/src/VBox/HostDrivers/VBoxUSB/win/cmn/VBoxUsbTool.cpp#L106)、[描述子失敗處理](https://github.com/VirtualBox/virtualbox/blob/1a6d24cb4a45f57aabfbad86811553e004f060f7/src/VBox/HostDrivers/VBoxUSB/win/mon/VBoxUsbFlt.cpp#L730)

因此下一個實驗改變的是「捕捉前先觀察到 D0」，而非反覆重啟、擴大 filter 或永久停用省電。

## 3. 單次喚醒與移交實驗

單純取得 radio handle／讀取資訊，未提供持續 D0 的證據。接著在精確指定的 radio 上進行一次 inquiry，timeout multiplier 設為 1，關閉 inquiry 與 radio handles 後立即讀取電源狀態，只在 `CM_POWER_DATA` 報告 D0（列舉值 1）時提出捕捉。這是一次實際 RF 操作；1.28 秒是 API 所定義的 inquiry 時間單位，不是整個作業的硬性最長執行時間。[Microsoft 搜尋參數說明](https://learn.microsoft.com/en-us/windows/win32/api/bluetoothapis/ns-bluetoothapis-bluetooth_device_search_params)

私有研究工具在 15:13 UTC 的紀錄如下：

- inquiry 回傳 0；捕捉前電源狀態為 1，相關 handles 已關閉。
- `usbattach` 回傳 0；VM 實際附掛清單確認目標。
- 主機出現 1 個 VirtualBox USB proxy；guest 有 2 個目標 USB 裝置，radio 的 BTHUSB／健康狀態檢查通過。兩筆 USB 列舉不代表有兩顆實體藍牙控制器。
- `usbdetach` 回傳 0，主機 radio 恢復檢查通過。
- 此次沒有配對，也沒有安裝實驗性 LDAC 驅動。

15:45–15:46 UTC 的後續 SDP 實驗也在捕捉前取得 D0、確認 VM 實際附掛，結束後 detach 回傳 0 且主機 radio 恢復健康狀態。這提供再次移交的實測證據，但不是預先規劃的大樣本成功率研究。

可支持的結論是：在這台筆電與此版本 VirtualBox，先經短 inquiry 並觀察到 D0 的程序，已讓原先失敗的控制器完成移交。仍不能宣稱永久修復所有冷啟動、休眠或其他控制器的情境；D0 取樣也不能證明後續每個時間點都保持 D0。長期停用選擇性暫停並未被採用，且沒有電池耗電量測結果。

## 4. 配對、SDP 與實際 Audio Sink PDO

操作者明確同意 VM 配對可能使主機需要重新配對，並將 XM6 設為配對模式。配對改變耳機端狀態，不能僅靠 VM snapshot 還原。以下失敗與成功分開保存：

| 程序 | 結果 | 解讀 |
| --- | --- | --- |
| 初次認證 | authentication result 1244 | 未取得成功證據 |
| 首次 callback 路徑 | result 1244；response 欄位仍為初始 sentinel | 未完成成功回應，不能當成耳機拒絕所有配對 |
| 修正回應路徑 | authentication result 0；callback method 3；I/O capability 3；response 0 | 本次 SSP 配對成功 |

修正後的回呼僅接受本次指定耳機及預期 method／I/O capability，呼叫 `BluetoothSendAuthenticationResponseEx` 時使用其選用 radio 參數的 null 路徑；不是改成接受所有耳機或任意驗證方式。API 必須用於回應已註冊 callback 收到的待處理認證請求。這次成功不能證明所有認證方式，也不能單憑前次失敗推定 Windows 內部鎖定的確切原因。[Microsoft 認證回應 API](https://learn.microsoft.com/en-us/windows/win32/api/bluetoothapis/nf-bluetoothapis-bluetoothsendauthenticationresponseex)

新 SDP probe 在 guest 使用 `NS_BTH`，要求 `LUP_FLUSHCACHE`，取得 `LUP_RETURN_BLOB`，並驗證查詢 GUID 與位址格式往返轉換。公開輸出只保留統計及狀態，不輸出遠端位址或原始 SDP blob。Audio Sink 查詢得到 **1 筆、67 bytes，error 0，enumeration_complete=true**。這是特定服務查詢完成的證據；並未解析或驗證全部 codec 能力。[Microsoft 服務列舉 API](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsalookupservicenextw)

另一項較廣的 L2CAP 服務查詢得到 **16 筆、1,547 bytes，error 234，enumeration_complete=false**。檢查 probe 原始碼後確認 `MAX_RECORDS=16`，達到上限時由工具主動設定 `ERROR_MORE_DATA`（234）並結束。因此這次是**有界探針的列舉上限**，不是「XM6 不支援 L2CAP」，也不是雙 L2CAP 音訊通道建立失敗。若日後需要完整服務目錄，應另訂適當的紀錄上限、時間及記憶體限制；本次不移除上限來美化結果。

同一輪 PnP 盤點確認實際 Audio Sink 服務 PDO：狀態 OK、problem code 0、服務 `BthA2dp`、INF `microsoft_bluetooth_a2dp_src.inf`，版本 `10.0.26100.1`。這證明 Windows stock profile 已經有服務裝置，並未證明 stock A2DP 播放或自製驅動運作。

特別需要處理的是：guest 觀察到的 Audio Sink hardware ID 使用 `LOCALMFG` 型式；目前 [OpenLdacTransport.inf](../../driver/OpenLdacTransport.inf) 匹配的是 XM6 機型 VID／PID 型式。不能假定目前 INF 可直接匹配，也不能為了載入而把公開 INF 擴大成所有同 radio 廠商的 Audio Sink。下一步需核實該服務的 hardware／compatible IDs、驅動排名與精確實例的實驗室綁定方法，保留原 stock profile 的還原路徑。

## 5. 公開工具的驗證與未完成工作

從成功私有程序整理出的 [vbox-warm-usb-trial.ps1](../../tools/vbox-warm-usb-trial.ps1) 將 VM、snapshot、VID／PID、radio instance 及唯一結果資料夾參數化。它不帶 guest 密碼、不操作配對、不啟停 VM、不改安全設定或永久電源政策。成功判定同時要求實際 VM 附掛、新健康 proxy、detach 成功及原主機 INF／服務／版本恢復；僅供 USB 層試驗。

第一輪公開工具實跑在 preflight 失敗，`capture_attempts=0`：Bluetooth class 中部分條目的選用 Service 屬性沒有 `Data`，StrictMode 因此拒絕存取。修正改為先檢查屬性是否存在，缺少／空值略過；真正查詢錯誤、多筆不明結果仍拒絕繼續。指定 radio 的唯一性及必須具有 BTHUSB 的必要基準未放寬。

語法與 9 項非硬體 fixtures 通過，涵蓋缺少屬性、缺少 Data、空值、BTHUSB、VBoxUSB、查詢例外、多筆結果、混合盤點與目標缺席。先前也完成 x64 結構尺寸 40／560／520、5 項附掛證據判斷與 2 項操作前拒絕測試。

修正後公開工具在 **15:49:57–15:51:10 UTC 完成一次實體試驗**：捕捉次數 1、inquiry 回傳 0、捕捉前 D0、handles 已關閉、實際 VM 附掛與新健康 proxy 同時成立、detach 回傳 0，且主機原 INF／服務／版本恢復檢查通過。判定為 `HOST_USB_TRIAL_PASSED_GUEST_UNVERIFIED`。工具本身的 `guest_gate` 仍是 `NOT_PERFORMED`，這次也沒有新增配對或安裝實驗性驅動；不能用其他私有測試的 guest 成功證據改寫這次工具的驗證範圍。

後續仍需逐項完成：

1. 核實 native SYS／INF／CAT 的來源、簽章及 guest-only 載入條件；不以合成 KernelLab 套件取代 production transport。
2. 處理實際 guest 服務 PDO 的精確綁定與復原，驗證真正的 BthPort profile interface。
3. 單次有界 AVDTP DISCOVER，再驗證 configure／OPEN／第二 L2CAP media channel／START；保存 callback、取消、關閉與資源退休證據。
4. 以短、低振幅 stereo WAV 開始實際播放，保留 HQ 優先與手動碼率；正常停止、斷線、重連及睡眠分開測試。
5. 取得可比較的音訊與功耗量測後，才討論日用筆電的音質、穩定性與耗電取捨；尚未建立 Windows 音訊端點或通過主機安裝門檻。

這次最有用的經驗是把「控制命令成功」、「裝置實際移交」、「服務存在」與「音訊播放」分別驗證；另一方面，探針自身的記錄上限與 PowerShell 空屬性錯誤也必須列入分析，避免把測試工具問題誤判成硬體不相容。
